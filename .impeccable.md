# Impeccable — SETI Design Context

This file is the single source of truth for design decisions in this project. All Impeccable skills (`craft`, `layout`, `typeset`, `colorize`, `polish`, etc.) MUST read this before any design work. When this file conflicts with the generic SKILL.md, **this file wins** — it is the project override.

---

## Design Context

### Users

Tabletop gamers who already know SETI: Search for Extraterrestrial Intelligence from the physical board game. They understand the game's rules, factions, and rhythms — they are here to play, not to learn. They expect the digital version to *preserve the ritual* of the tabletop experience (card geometry, faction colors, resource economy) while replacing only the manual overhead (bookkeeping, setup, state tracking).

Context of use: focused sessions at a computer, dark room, multi-player online. Not mobile-first, not a quick-check dashboard tool.

Job to be done: play a game of SETI with other people, end-to-end, without friction, while preserving the Space Agencies expansion premise: powerful public, private, and fringe organizations competing to shape the search for alien life and make first contact.

### Brand Personality

Three anchor words:

- **Cutting-edge** — current-decade sci-fi, not retro CRT nostalgia, not Star Trek pulp. Precision hardware, not fantasy.
- **Scientific** — instrumentation, readouts, coordinates, frequency dials. Every number feels *measured*, not decorative.
- **Cosmic** — the void is the canvas, but the canvas is *alive*: nebula light, stellar drift, the faint hum of deep-space radio. Darkness is layered, not flat.

Tone in copy: economical, factual, and organization-centered. Avoid gamification cheer ("Great job!"), avoid marketing fluff, avoid cute. Use the language of the Space Agencies rulebook: organizations, missions, quick starts, alien species, signal tokens, and first contact. Do not drift into generic terminal, observatory, dossier, channel, or watch-room metaphors.

Emotional goal: calm concentration punctuated by moments of quiet awe when a signal is detected.

## The Three Problems We Are Solving

This section names the failure modes of the current UI explicitly so every future change is measured against them.

**Problem 1 — The screen reads as a flat black rectangle.** Pure `#000` with one accent does not feel like space; it feels like a terminal. Real deep-space imagery is *not* uniform black. It has a faint violet-to-cyan gradient from background radiation, dust-lane occlusions, and the soft scatter of unresolved stars. **The fix**: layered cosmic darkness (§ Cosmic Atmosphere), a small but deliberate palette of *signal colors* beyond anodized blue (§ Signal Palette), and surfaces that visibly sit at different depths above the void.

**Problem 2 — UI copy reads like a generic web form or the wrong sci-fi metaphor.** "Submit", "Cancel", "Settings", "Terminal", "Dossier", and "Briefing Room" either feel like a checkout flow or like a generic observatory console. **The fix**: the Space Agencies lexicon (§ Voice & Lexicon). The interface speaks about organizations competing for first contact, while keeping common interaction controls plain when flavor would slow comprehension.

**Problem 3 — Components look like default Tailwind, not instruments.** Rounded rectangles, flat borders, default focus rings. **The fix**: the instrument-grade component recipes (§ Component Vocabulary). Every interactive surface is either an anodized-metal control, a luminous readout, or a signal indicator — and nothing else.

## Aesthetic Direction

**High-level metaphor**: a Space Agencies mission interface for powerful organizations entering the search for alien life. Ambient darkness with focused pools of instrument light. The interface should feel like the shared digital table where players choose missions, organizations, quick starts, and paths toward first contact — not a fake terminal or archive room.

**Theme**: dark, always. No light mode. Darkness is a brand pillar, not a preference.

### Visual Snapshot — Mission Hub / Design System

Reference: the user-provided `2223.PNG` visual snapshot. Treat this snapshot as the current north star for the Mission Hub homepage and design-system sample screens.

The snapshot reads as a **low-poly cinematic mission interface**: deep-space black, faceted lunar terrain, a white spacecraft, a lone astronaut, orange planetary geology, and cyan engine light. It is not a SaaS dashboard and not a terminal. The first screen should feel like a playable SETI staging area with real world-building assets, not a marketing hero or generic admin shell.

**Snapshot palette anchors**:

| Snapshot name | Hex | Role |
|---|---|---|
| Deep Space Black / 深空黑 | `#0A0E14` | Root background and void depth. |
| Rock Gray / 岩石灰 | `#1A1F27` | Dark surface blocks and header chrome. |
| Metal Gray / 金属灰 | `#2A303C` | Borders, inactive controls, secondary panels. |
| Terrain Gray / 地表灰 | `#3A404D` | Low-poly terrain, card image overlays, raised gray detail. |
| Stardust White / 星尘白 | `#E6E6E8` | Primary text, spacecraft highlights, numeric clarity. |
| Planet Orange / 行星橙 | `#C7734A` | Planet geology, in-progress tags, warm focal contrast. |
| Engine Cyan / 引擎青 | `#2EC1C9` | Primary actions, active tabs, selected controls, engine light. |

Implementation can translate these to OKLCH tokens, but preserve the relationships: black is layered, gray is faceted, white is slightly softened, orange is geological warmth, cyan is active instrumentation.

**Homepage optimization rules from the snapshot**:

1. **Top bar is quiet chrome.** Logo left; locale, text-mode switch, current area, user identifier right. Height stays compact with a 1px divider. Do not turn navigation into a large hero element.
2. **Hero is an environment plus controls.** The Mission Hub title sits over a full-width low-poly space scene. A small availability label, subtitle, and a single `Create Mission` action are enough. The ship, astronaut, and terrain carry the emotion.
3. **Metrics are mission-state tiles, not generic stats.** Use three desktop cards for waiting, in-progress, and participating missions. Each card has a cropped low-poly background, one status dot, a large two-digit Orbitron count, and one short label. The value color carries state: cyan for available, violet for active/in-progress, green for participating/confirmed.
4. **Mission list is compact and scannable.** Tabs sit directly above room cards. Room cards show room name/id, host, player count, module, and status tag without extra explanation text. The cards are dark image-backed panels with 1px borders and small radii.
5. **Background elements are reusable art assets.** Planets, faceted rocks, astronaut, rover, spacecraft, and lunar structures should be treated as a small visual asset kit. Reuse them to tie screens together; do not replace them with abstract gradients, blobs, or decorative SVG lines.
6. **First viewport must reveal the product.** Users should immediately see "Mission Hub", current mission counts, live rooms, and a hint of the world below. Avoid a standalone landing-page hero that hides the room list below the fold.

**Component details visible in the snapshot**:

- Buttons: cyan filled primary, transparent outline secondary, dark ghost. Keep labels short and action-specific.
- Tags: amber for in-progress, cyan/green for waiting/ready, gray for single-player or neutral state. Tags are semantic, not decorative badges.
- Inputs/selects: dark rectangular fields, 1px border, subtle focus state, no glow-heavy glassmorphism.
- Switches/checkboxes/radios: cyan active fill with white indicator, sized for scanning rather than spectacle.
- Icons: thin outline icon set, consistent stroke, white/gray by default. Use icons as tools, not decorations.
- Pagination: compact square controls with cyan active state and simple chevrons.

### Cosmic Atmosphere — the base layer

The page background is **never** a single solid color. It is a composition of three layers, painted from back to front:

1. **Void gradient** (the canvas). A very subtle radial gradient — not a vignette, not a glow — centered slightly off-axis, drifting from a deep indigo-violet at the focal point to a colder near-black at the edges. This is *barely* perceptible; it does the work of suggesting depth without ever being noticed.
   ```css
   background:
     radial-gradient(ellipse 120% 80% at 38% 28%,
       oklch(0.16 0.035 280) 0%,
       oklch(0.12 0.025 265) 45%,
       oklch(0.08 0.018 255) 100%);
   ```
2. **Stellar field** (the texture). A static, low-opacity SVG or canvas starfield layered above the gradient at ~12% opacity. Stars are tiny (0.5–1.5px), unevenly distributed, a mix of warm-white and faint blue-white. **Static, not animated** — twinkling is kitsch. Generate once at app boot; cache as a data URI.
3. **Dust lane** (the depth cue). A single, very faint diagonal smear of slightly warmer noise (`oklch(0.22 0.04 30 / 0.04)`) running across one third of the viewport, suggesting the plane of a galaxy. Optional, used on hero/landing screens only.

Panels, cards, and dialogs sit *above* this composition with their own surface lightness (see § Surface System), creating the read "the interface is floating in space, not painted on a black wall."

### Surface System — depth through lightness, not shadow

Five named surface levels. Pick one per component; never invent in-between values.

| Token | OKLCH | Use |
|---|---|---|
| `--surface-void` | `oklch(0.10 0.02 260)` | The base layer, behind the cosmic atmosphere composition. Almost never used as a component fill. |
| `--surface-deep` | `oklch(0.15 0.028 262)` | App chrome (top bar, side rails). The first thing that *lifts* off the void. |
| `--surface-panel` | `oklch(0.19 0.032 262)` | Default panel and card fill. The workhorse surface. |
| `--surface-raised` | `oklch(0.24 0.036 262)` | Modals, popovers, dropdowns — anything that floats above panels. |
| `--surface-instrument` | `oklch(0.13 0.025 258)` | Inset readouts (telemetry tiles, data wells). *Darker* than its container, like a recessed display. |

The interplay matters: a telemetry readout (`instrument`) inset into a card (`panel`) inset into the app chrome (`deep`) floating on the void creates four perceived depth planes without a single drop-shadow.

### Signal Palette — the expanded accent system

The old rule ("one accent, anodized blue") was correct for chrome but starved the interface of life. Replace it with a **signal palette**: a small set of meaning-bound accents that appear *only* when their meaning is active.

| Signal | Name | OKLCH | Reserved for |
|---|---|---|---|
| 🔷 | **Anodized Blue** | `oklch(0.68 0.11 240)` | Player agency: active turn, primary actions, focused interactive elements, current selection. The chrome accent. |
| 🟣 | **Nebula Violet** | `oklch(0.62 0.14 305)` | Discovery events: new signal detected, alien encountered, mission objective revealed. The "awe" accent — rare and luminous. |
| 🟢 | **Ion Green** | `oklch(0.78 0.13 155)` | Confirmed / acquired / nominal status. Used on diagnostic dots, success readouts, lock-on indicators. Never on buttons. |
| 🟡 | **Signal Amber** | `oklch(0.78 0.13 75)` | Caution, pending action, decaying resource, low fuel. Telemetry warnings, not error states. |
| 🔴 | **Plasma Red** | `oklch(0.65 0.18 25)` | Critical failure, destructive action confirm, mission abort. Used sparingly — when red appears, it *means* something. |
| ⚪ | **Phosphor White** | `oklch(0.96 0.008 260)` | Data readouts. Plain, mono, never another color. Data is honest instrumentation. |

**Rules of the signal palette:**
- A signal color earns its place by *meaning*, not aesthetics. Don't tint a button violet because violet looks nice — tint it violet only if pressing it acquires a signal.
- Two signal colors should rarely appear in the same component. If your tooltip has violet, green, and amber dots, you have three meanings competing for the same eye.
- Signal colors get a faint matched glow (see § Luminous Effects). Chrome (anodized blue) never glows — it reflects.

### Alien-Faction Palette (locked content color — never chrome)

Centaurians, Exertians, Mascamites, Oumuamua, Amoeba, Glyphids, Anomalies — use the existing hex values from `tailwind.config.ts`. Treat them as *content color* (like a map legend), not *interface color*. The interface chrome stays in the Signal Palette above regardless of which faction is in focus.

### Luminous Effects — glow with restraint

Glow is a verb, not a decoration. Reserve it for moments of *signal*, never for chrome.

- **Signal glow** (a discovery dot, a new-event ping, a detection indicator):
  ```css
  box-shadow:
    0 0 8px var(--signal-glow-color, oklch(0.62 0.14 305 / 0.6)),
    0 0 24px var(--signal-glow-color, oklch(0.62 0.14 305 / 0.25));
  ```
  Pair with a slow 2.4s `ease-in-out` opacity pulse (60% ↔ 100%) for active signals.
- **Focus glow** (keyboard focus on interactive elements): a 2px outer ring in anodized blue at 50% opacity. Tight, deliberate, never feathered.
- **Forbidden**: ambient glow around panel borders, glowing text shadows on headings, neon-on-dark gradient washes, anything that reads as "VR menu in a movie."

## Voice & Lexicon — Space Agencies dictionary

The single biggest immersion lever. Use Space Agencies language when it clarifies the game concept, and use standard product language when flavor would become opaque. **Always check this table before naming any new button, label, status, or screen.**

### Verbs (button labels, primary actions)

| Don't write | Write instead | Notes |
|---|---|---|
| Submit | **Create Mission** / **Join Mission** / **Start Mission** | Use the specific user action, not a decorative verb. |
| Confirm | **Confirm** | Keep plain unless the action is a concrete game action. |
| Cancel | **Cancel** | Standard interaction label is clearer than flavor here. |
| Save | **Save** | Profile/account/settings actions should stay familiar. |
| Delete | **Delete** / **Remove** | Use destructive clarity over flavor. |
| Retry | **Try again** | Plain recovery language is best. |
| Continue / Next | **Next** | Preserve normal form flow language. |
| Back | **Back** / **Mission Hub** | Prefer destination labels when useful. |
| Settings | **Mission Settings** | Do not call this "Calibration" unless it is a debug/calibration tool. |
| Login / Logout | **Sign In** / **Sign Out** | Avoid terminal/access metaphors. |
| Loading… | **Loading missions…** / **Loading actions…** | State what is being loaded. |
| Coming soon | **Not available yet** | Plain, actionable status. |

| Don't write | Write instead |
|---|---|
| Player / User | **Player** in rules/gameplay, **Member** in account/profile copy |
| Players (list) | **Players** |
| Turn | **Turn** |
| Round | **Round** |

| Score | **Score** or **Mission yield** only when the scoring context is clearly final/result-oriented |

| Cards (hand) | **Hand** |

| Notifications | **Notifications** |
| Help | **Rules** or **Field Manual** |
| Tutorial | **Quick Start** only when it refers to the expansion cards; otherwise **Tutorial** |
| Online (status) | **Signed in** |
| Offline | **Signed out** |
| Disconnected | **Disconnected** |
| Organization module | **Space Agency / Organization** |
| Create-room surface | **Create Mission** |

### Rules of the lexicon

1. **Space Agencies, not generic sci-fi.** If a term could belong to any space terminal ("dossier", "uplink", "watch", "briefing room"), it is probably wrong unless the Space Agencies rulebook supports it.
2. **Don't translate everything.** "Cancel", "Save", "Profile", "Turn", and "Players" stay plain when that helps the user act quickly.
3. **Consistency over cleverness.** Use "Mission Hub" for the pre-game list, "Create Mission" for room creation, "Players" for seats, "Organization" for the expansion choice, and "First Contact" for the premise.
4. **Tone is factual, not movie-trailer.** Write "Choose an organization before the mission begins", not "Your agency awakens among the stars."

## Typography

- **Display / Latin readout**: `Orbitron` (Google Fonts). Use for the SETI wordmark feeling, homepage titles, English micro labels, status numerals, and compact readouts. It should feel technical and measured, not retro-terminal.
- **Chinese body / UI**: `Noto Sans SC` (Google Fonts). Use for Chinese navigation, labels, room metadata, form text, and body copy. It keeps the Chinese interface sharp without fighting Orbitron.
- **Dense mono fallback**: `JetBrains Mono` (Google Fonts) only when a value is truly technical and dense: coordinates, frequencies, timestamps, raw logs. Do not use it for homepage counters or ordinary UI chrome.

Type scale: fixed `rem` scale with a 1.25 ratio minimum between steps. No `clamp()` on product chrome.

**Two project-specific type rules:**

1. **Mission-log labels** (the small labels above a readout — e.g. "可加入任务", "COLOR PALETTE", "PLAYERS") use Noto Sans SC for Chinese and Orbitron for English at 0.6875rem, uppercase for English only, letter-spacing `0.08em`, color `oklch(0.62 0.02 260)`. They are the connective tissue of every panel and they look like instrument-panel labels.
2. **Numeric readouts** use Orbitron with `font-variant-numeric: tabular-nums`. Use JetBrains Mono only for dense coordinates/frequencies/logs where slashed zero and fixed-width columns matter more than the snapshot's visual identity.

## Component Vocabulary

The small, closed set of UI patterns that the entire interface is built from. **Do not invent new components without first checking whether one of these covers it.** Atmospheric consistency comes from a *limited* vocabulary applied carefully, not from a sprawling design system.

### 1. Panel

The workhorse. A rectangular surface at `--surface-panel`, wrapped in a hairline metal border (§ Metal Surfaces below), with internal padding from the spacing scale. Title row at the top uses a mission-log label on the left and an optional status dot on the right.

### 2. Telemetry Tile

A panel-within-a-panel. Recessed surface (`--surface-instrument`), Orbitron readout in Phosphor White or semantic signal color at large size (e.g. `2.25rem`), mission-log label above. Used for: score, resources, round/turn counters, mission counts, or coordinates. Always grouped in clusters of 2–6 in a CSS grid, never standalone.

### 3. Signal Indicator

A small 8px dot with a matched signal-color glow (§ Luminous Effects). Status meaning is encoded in color, with a textual label adjacent (never color-only — fails colorblind safety even though we don't formally target WCAG). Pulse slowly when "active"; static when "nominal" or "off."

### 4. Metal Control (primary button)

See § Metal Surfaces. The anodized-blue metal face. Use sparingly — typically one per screen, the *primary action of this moment*. Label the real action clearly ("Create Mission", "Join Mission", "Start Mission"), not with decorative control-room verbs.

### 5. Ghost Control (secondary button)

Hairline metal border + transparent face. Label color: `oklch(0.85 0.012 260)`. Hover fills with `oklch(0.22 0.03 260 / 0.5)`. No glow, no metal face. The default action for *most* clickable things.

### 6. Instrument Selector (tabs / segmented control)

A row of ghost-control segments inside a hairline-bordered track. The active segment swaps to the metal control face (anodized blue). Used for: phase tabs, view toggles, faction filters in the lobby.

### 7. Readout Row

A single horizontal row: mission-log label on the left, tabular value on the right, optional signal indicator at the far right. Used for any "key: value" data — player stats, mission parameters, log entries.

### 8. Bulletin (toast / notification)

A panel that slides in from the top-right with: mission-log timestamp (mono, dim), label/title (one line, sentence case), optional body (one line max), optional signal-color left-edge stripe **at 1px only** (this does not violate the side-stripe ban — the ban is on stripes > 1px used decoratively; a 1px signal-color hairline is part of the panel border treatment, not a decorative accent).

### 9. Transmission Overlay (modal)

A centered `--surface-raised` panel above a 70%-opacity void backdrop. Header uses a plain context label ("Create Mission", "Confirm Delete", "Profile"). Always include explicit action and cancel controls. The backdrop click default is cancel/close; destructive actions must require deliberate input.

### 10. Scanline (loading state)

A single 1px horizontal line in anodized blue at 40% opacity sweeping vertically across the loading container over 1.6s, exponential ease-out, infinite. **Only** for loading states ("Establishing uplink…"). Never decorative. Pair with a mission-log status message that updates as state changes ("Establishing uplink…" → "Acquiring telemetry…" → "Synchronizing roster…"). Static loading text is a missed atmosphere opportunity.

## Metal Surfaces

The defining tactile quality. Borders and interactive surfaces feel like anodized/brushed metal panels lit from above. Restrained skeuomorphism — *engineered*, never Aqua.

**Hairline metal border** (default for panels, inputs, dividers — the workhorse):

```css
border: 1px solid transparent;
border-image: linear-gradient(
  to bottom,
  oklch(0.55 0.04 240) 0%,
  oklch(0.32 0.03 240) 50%,
  oklch(0.22 0.025 240) 100%
) 1;
box-shadow: inset 0 1px 0 oklch(0.78 0.04 240 / 0.25);
```

Alternative for rounded corners (where `border-image` breaks): 1px solid `oklch(0.34 0.035 240)` plus a layered `box-shadow` with both an inset highlight (top) and inset shadow (bottom).

**Metal control face** (primary CTAs, active-turn indicators):

```css
background: linear-gradient(
  to bottom,
  oklch(0.58 0.10 240) 0%,
  oklch(0.50 0.09 240) 50%,
  oklch(0.44 0.08 240) 100%
);
border: 1px solid oklch(0.30 0.06 240);
box-shadow:
  inset 0 1px 0 oklch(0.78 0.07 240 / 0.5),
  inset 0 -1px 0 oklch(0.22 0.05 240 / 0.6),
  0 1px 0 oklch(0.1 0.02 260 / 0.8),
  0 0 0 1px oklch(0.2 0.04 240 / 0.4);
color: oklch(0.98 0.01 240);
/* hover: brighten gradient 4–6% in lightness, unchanged chroma */
/* active (pressed): invert — darker top, lighter bottom, drop contact shadow */
```

**Metal rules:**
- Metal borders are always **cooler than** the surface they sit on. Warm metal = brass = wrong metaphor.
- Never combine a metal gradient with a glow. Metal reflects; it doesn't emit. Glow belongs to signals, not chrome.
- Confine metal to: borders (hairline), primary buttons, active-state indicators, slider tracks/handles, toggle switches. Do NOT metallize every surface — overuse kills the effect immediately.
- A panel background is NOT metal. Panels are dark surface; metal is only their frame.

## Motion

Restrained. One well-orchestrated moment of reveal (signal detection, turn transition, end-of-round) is worth more than ten hover twitches.

- **Easing**: exponential ease-out for entrances; linear for continuous (scanlines, pulses). **No bounces, no elastic, ever.**
- **Duration vocabulary**: micro (120ms — hover state changes), short (240ms — button press, dropdown open), medium (480ms — panel reveal, transmission overlay enter), long (1200–1800ms — signal-detection reveals, end-of-mission). Pick from these four; don't invent in-between numbers.
- **Signal pulse**: opacity 60% ↔ 100% over 2.4s, ease-in-out, infinite. This is the *only* infinite motion in chrome.
- **Reduced motion**: honor `prefers-reduced-motion` by default — disable scanlines, signal pulses, and reveal staggers. Snap to end state.

## Decorative Vocabulary

Purposeful, not decorative:

- Subtle static starfield in the cosmic atmosphere layer (§ Cosmic Atmosphere).
- Signal-waveform divider (a single thin line with a faint amplitude) as an occasional section break — at most 1–2 per screen.
- Instrument-style tick marks for sliders, timers, and phase progress.
- Mission-log labels are themselves decoration *and* function — they do double duty.
- SETI sprite kit: use `packages/client/public/assets/seti/sprites/objects_00_00.webp` through `objects_02_02.webp` and `terrain_00_00.webp` through `terrain_02_02.webp` as first-class low-poly placeholder/decorative/background assets. `objects_*` are 3×3 scene/object crops for spacecraft, astronaut, rover, antenna, planets, and orbital structures; `terrain_*` are 3×3 terrain/environment crops for faceted lunar ground, rocks, bases, planets, and impact scenes. They are appropriate for card decoration, mission-card image wells, room-card background fills, hero/environment panels, and low-opacity texture layers. Preserve their square aspect ratio, crop with `object-fit: cover`, and do not stretch them non-uniformly.

Do NOT: use HUD corner accents on every panel; use grid overlays everywhere; use glassmorphism as chrome.

## Design Principles (the load-bearing five)

1. **Signal over noise.** Dark by default. Only what's relevant *right now* is luminous. Accents are rare; their power comes from scarcity, not saturation.
2. **Instrumentation, not decoration.** Numbers, coordinates, counts, statuses — rendered like lab instruments. Mono, aligned, tabular, precise. Never dressed up as marketing stat tiles.
3. **Depth through cosmic darkness and metal.** Three depth techniques only: the layered cosmic atmosphere behind everything, stepped OKLCH lightness for surfaces, hairline metal borders for edges. No drop-shadows for hierarchy; no glow for chrome.
4. **Signal palette, not theme palette.** Anodized blue = player agency. Violet = discovery. Green = confirmed/ready. Amber = pending/caution. Red = critical/destructive. Data = mono white. A color earns its place by meaning; if it has no meaning, it has no place.
5. **The lexicon is half the design.** Organization, mission, quick start, alien species, signal token, first contact. The words *are* the atmosphere as much as the pixels. Generic terminal/observatory copy will sabotage a perfect visual.
6. **Card geometry is sacred.** Game-card dimensions, aspect ratios, visual styles, and faction colors are immutable. Design *around* them. Never restyle them to fit a layout — restructure the layout instead.

## Anti-References — explicitly not this

- Not a **SaaS dashboard**. No metric tiles with a big number + tiny label + sparkline. No "At a glance" cards. No Linear/Vercel-admin aesthetic.
- Not **Mars colonization** / Terraforming Mars rust-on-dark. The existing `brand-guidelines` skill describes a different project; ignore its Mars palette for this codebase.
- Not **retro sci-fi** (no CRT scanlines decoratively, no 80s neon, no Star Wars wipes). The single scanline used for loading is a *function*, not nostalgia.
- Not **cute / gamified** (no mascots, no confetti on actions, no rounded-pastel everything).
- Not **generic dark mode with glowing purple-to-cyan gradients**. That is the #1 AI-slop tell.
- Not **VR-movie HUD** (no spinning rings, no corner brackets on every panel, no Helvetica-on-glow). This is a Space Agencies mission interface, not a fictional terminal.

## Implementation Constraints

- **Only target**: `packages/client` (Vite + React 18 + Tailwind v4). `packages/web` (Next.js) is out of scope for new design work.
- **Accessibility bar**: keep it simple. No formal WCAG target, no colorblind-safe remapping of faction colors. Don't over-engineer — but don't regress below sensible defaults (keyboard focus visible, form labels present, reasonable contrast on text, signal meaning always paired with a textual label).
- **Existing dependencies to use**: `@radix-ui/react-select`, `class-variance-authority`, `clsx`, `tailwind-merge`, `zustand`, `@tanstack/react-router`, `@tanstack/react-query`. Do not introduce new UI libraries without reason.
- **Sacred files — do not restyle**:
  - `packages/client/src/styles/globals.css` — the `.seti-sector-grid` and `.cgo-*` / `.card-*` classes are game-card rendering. Do not touch.
  - Any card component that renders game cards directly.
- **Fonts**: load `Orbitron`, `Noto Sans SC`, and `JetBrains Mono` from Google Fonts. Remove the current `Ubuntu` import from `globals.css` once all usages are migrated. Keep JetBrains Mono as the dense-data fallback, not the default UI voice.
- **Color tokens**: migrate `packages/client/src/config/theme.ts` to the OKLCH values described above. Keep the shape of `THEME_TOKENS`; change the values. Add the new tokens (`--surface-*`, `--signal-*`) as additions, not replacements.

## When In Doubt

Ask these three questions, in order:

1. **"Does this element support the Space Agencies premise, or is it a generic sci-fi terminal/dashboard?"** If the latter, rebuild it.
2. **"Does this label help players understand a mission, organization, setup, or rule choice?"** If not, simplify it.
3. **"If I removed this color / glow / animation, would the interface lose meaning, or just lose decoration?"** If decoration, remove it.
